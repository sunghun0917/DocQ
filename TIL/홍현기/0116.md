# 오늘의 TIL
### 웹 아키텍처 패턴: SSR vs CSR 그리고 프로젝트의 방향성

### 1. 아키텍처에 대한 의문
보통 웹 서비스는 Nginx(정적) + Spring(동적)으로 나눈다고 생각했는데, 왜 중간에 Node.js(Vue/Next.js) 서버를 하나 더 껴서 Nginx -> Node -> Spring으로 만드는 경우가 있을까?

핵심 이유: SSR (Server-Side Rendering) & BFF
단순히 파일을 주는 게 아니라, 서버에서 HTML을 조립해야 하는 경우 중간 서버(Node)가 필요하다.

SEO (검색 엔진 최적화): 구글/네이버 봇에게 꽉 찬 HTML을 줘야 검색 상위에 노출됨.

초기 로딩 속도: 빈 화면(White screen) 없이 완성된 화면을 바로 보여줌.

BFF (Backend For Frontend): 프론트엔드 입맛에 맞게 여러 API를 합치거나(Aggregation), 보안 키를 숨기는(Token Hiding) 중간상인 역할.

### 2. SSR vs CSR 완벽 비교
CSR (Client-Side Rendering)
"빈 접시(HTML) 먼저 받고, 요리(Data)는 나중에 받아서 손님이 직접 담는다."

구조: User → Nginx(정적 파일 제공) → Browser(렌더링) ↔ Spring(API)

특징:

초기 로딩 시 흰 화면이 뜰 수 있음.

한 번 로딩되면 페이지 이동 시 깜빡임 없이 매우 부드러움 (App-like).

서버 부하가 적고 비용이 저렴함 (S3, Nginx만 있으면 배포 가능).

적합한 서비스: 관리자 페이지(Admin), 대시보드, 게임, 사내 시스템.

SSR (Server-Side Rendering)
"주방장(Server)이 요리가 담긴 접시(완성된 HTML)를 서빙한다."

구조: User → Nginx → Node Server(HTML 조립) ↔ Spring(API)

특징:

검색 엔진(SEO)에 매우 유리함.

카톡/슬랙 공유 시 썸네일(메타 태그)이 잘 나옴.

페이지 이동 시마다 서버 요청이 발생해 약간의 끊김이 있을 수 있음.

적합한 서비스: 쇼핑몰(커머스), 뉴스, 블로그, 채용 사이트.

### 3. 내 프로젝트(보드게임 웹)의 아키텍처 결정
🎯 결론: CSR (Client-Side Rendering) 선택!
이유:

게임의 특성: 보드게임은 '검색 노출'보다 **'실시간 반응성'**과 **'부드러운 화면 전환'**이 생명이다.

화면 깜빡임 방지: 게임 도중 화면이 새로고침 되면 몰입감이 깨진다.

WebSocket 유지: CSR은 페이지가 유지되므로 소켓 연결 관리가 훨씬 수월하다.

불필요한 오버헤드 제거: 비공개 게임방의 내용을 구글이 검색할 필요가 없다.
