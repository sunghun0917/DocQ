## 🔍 문제 상황

FastAPI 기반 AI 서비스에서 PDF 업로드 → GPU 처리 → 결과 반환하는 비동기 작업 시스템 구축 중 발생한 문제

### 증상
- 새로운 HTTP 요청 없이 `run_gpu_job`이 반복 실행됨
- `FileNotFoundError: PDF not found: /tmp/tmp75827n1p.pdf`
- 무한 재시도 루프 발생

## 🧠 근본 원인 분석

### 1. Redis 영속성 vs /tmp 휘발성 불일치

| 구성 요소 | 영속성 | 컨테이너 재시작 후 |
|-----------|--------|-------------------|
| Redis 큐 (appendonly yes + volume) | ✅ 영속 | 데이터 유지 |
| /tmp/*.pdf 파일 | ❌ 휘발성 | **삭제됨** |

```python
# 문제의 코드
job = {
    "jobId": "abc123",
    "pdf_path": "/tmp/tmp75827n1p.pdf"  # ← 컨테이너 재시작 시 사라짐
}
```

### 2. 앱 시작 시 스케줄러 자동 실행

```python
@app.on_event("startup")
def startup():
    start_scheduler()  # ← 무한 루프로 Redis 큐 polling
```

### 3. 무조건 재큐잉하는 예외 처리

```python
except Exception:
    enqueue(job)  # ← 영구적으로 복구 불가능한 오류도 재큐잉 → 무한 루프
```

## ✅ 해결책

### 1. AI 전용 Redis 분리 (영속성 OFF)

```yaml
# docker-compose.yml
ai-redis:
  image: redis:7-alpine
  # appendonly 없음 = 재시작 시 데이터 초기화
  # volumes 없음 = 컨테이너 내부에만 데이터 존재

ai-service:
  environment:
    - REDIS_HOST=ai-redis
```

**효과**: 컨테이너 재시작 시 /tmp 파일과 Redis 큐가 **동시에 초기화** → 불일치 해결

### 2. 파일 존재 확인 + 재큐잉 제거

```python
# 파일 존재 확인
if not pdf_path or not os.path.exists(pdf_path):
    logger.error(f"PDF not found: {pdf_path}")
    send_callback(job["jobId"], "failed", error="PDF file not found")
    continue  # 재큐잉 없이 건너뜀

# 실패 시에도 재큐잉하지 않음
except Exception:
    send_callback(job["jobId"], "failed", error="Processing failed")
    # enqueue(job) ← 제거
```

### 3. 작업 완료 후 파일 정리

```python
finally:
    release_worker(port)

        os.remove(pdf_path)  # /tmp 디스크 공간 확보
```

## 🔄 결과 전달 방식 비교

### 방법 1: Polling (Spring Boot → AI 서비스)
```
Spring Boot가 주기적으로 결과 조회 API 호출
- 장점: AI 서비스 단순
- 단점: 불필요한 요청, 지연 발생
```

### 방법 2: Redis 직접 조회
```
Spring Boot가 ai-redis에 직접 연결
- 장점: 약간 빠름
- 단점: 결합도 높음, 설정 복잡
```

### 방법 3: Webhook (채택) ⭐
```
AI 작업 완료 시 Spring Boot에 HTTP 요청
- 장점: 즉시 알림, 불필요한 요청 없음, 간단
- 단점: 콜백 실패 시 처리 필요
```

```python
# AI 서비스에서 작업 완료 시
requests.post(
    "http://backend:8080/ai/callback",
    json={
        "jobId": job["jobId"],
        "status": "completed",
        "quizzes": result["quizzes"]
    }
)
```

```java
// Spring Boot에서 콜백 수신
@PostMapping("/ai/callback")
public ResponseEntity<Void> handleAiCallback(@RequestBody CallbackRequest request) {
    Room room = roomRepository.findByAiJobId(request.getJobId());
    room.setQuizList(convertToQuizzes(request.getQuizzes()));
    // WebSocket으로 클라이언트에 알림
}
```

## 📊 아키텍처 최종 흐름

```
1. 클라이언트 → Spring Boot: PDF 업로드
          ↓
2. Spring Boot → AI Service: POST /ai/upload/pdf
          ↓
3. AI Service: 큐에 등록, 즉시 {jobId} 응답
          ↓
4. Spring Boot: room.setAiJobId(jobId) 저장
          ↓
5. AI Scheduler: GPU 작업 실행
          ↓
6. AI Service → Spring Boot: POST /ai/callback (Webhook)
          ↓
7. Spring Boot: findByAiJobId(jobId) → room 찾아서 퀴즈 저장
          ↓
8. WebSocket → 클라이언트: 완료 알림
```

## 💡 핵심 교훈

### 1. 데이터 라이프사이클 일치시키기
> Redis 영속성과 파일 시스템의 라이프사이클이 다르면 불일치 발생

### 2. 방어적 프로그래밍
```python
tmp_path = None  # 예외 발생 시 NameError 방지
try:
    tmp_path = save_file()
except:
    if tmp_path and os.path.exists(tmp_path):
        os.remove(tmp_path)
```

### 3. 실패 결과도 저장해야 함
> 비동기 작업에서 성공/실패 모두 클라이언트가 알 수 있어야 함

### 4. 재시도는 신중하게
> 복구 불가능한 오류(파일 없음)는 재시도하면 안 됨

### 5. Webhook > Polling
> 이벤트 기반 알림이 주기적 폴링보다 효율적

### 6. 좀비 TCP 해결
MinerU 연결 고갈 (Connection Exhaustion)
netstat -an | findstr 18000# 수십 개의 CLOSE_WAIT, FIN_WAIT 연결 ❌
MinerU가 재시작 루프에 빠짐 → 연결이 제대로 정리 안 됨
TCP 좀비 연결 누적 → 새 연결 불가
해결: Docker Desktop 재시작
