
## EC2 Docker 컨테이너에서 로컬 PC Docker 컨테이너로 API 요청 보내기

### (SSH Reverse Tunnel + Docker + UFW 정리)

---

## 1. 상황 요약

* **EC2 서버**

  * docker-compose로 `ai-service` 컨테이너 실행 중
* **로컬 PC**

  * Docker 컨테이너로 `MinerU` 실행 중
  * `localhost:18000` 에서 PDF 파싱 API 제공

### 목표

> **EC2의 ai-service 컨테이너 → 로컬 PC의 MinerU 컨테이너로 API 요청을 보내고 싶다**

일반적인 서버 구조와 반대 방향의 통신이다.

---

## 2. 왜 바로 연결이 안 되는가?

* 로컬 PC는 NAT 뒤에 있음
* EC2에서 로컬 PC로 직접 접근 불가능
* 로컬 PC에 공인 IP/포트 개방 ❌

👉 **중간 경유지(터널)가 필요**

---

## 3. 해결책: SSH Reverse Tunnel

사용한 명령어:

```bash
ssh -i I14D209T.pem -N \
  -R 0.0.0.0:18000:localhost:18000 \
  ubuntu@i14d209.p.ssafy.io
```

### 이 명령의 정확한 의미

* **EC2의 0.0.0.0:18000** 으로 들어오는 요청을
* SSH reverse tunnel을 통해
* **로컬 PC의 localhost:18000 (MinerU)** 로 전달

즉:

```
EC2:18000  ──(SSH 터널)──▶  Local PC:18000 (MinerU)
```

EC2 입장에서는 18000 포트에 서버가 있는 것처럼 보이지만,
실제 처리는 로컬 PC에서 이루어진다.

---

## 4. ai-service에서 EC2_HOST_IP가 필요했던 이유

`ai-service`는 **Docker 컨테이너**다.

컨테이너 내부에서:

* `localhost` → 컨테이너 자기 자신
* 로컬 PC ❌
* EC2 host ❌

그래서 ai-service는 **반드시 EC2 host를 중간 관문으로** 접근해야 했다.

이를 위해 사용한 환경변수:

```env
EC2_HOST_IP=172.26.15.66   # EC2 private IP
```

의미:

> “로컬 MinerU로 가기 위한 중간 경유지(host) 주소”

---

## 5. IP 하드코딩 제거: `host.docker.internal`

Linux(EC2)에서는 기본 제공되지 않으므로 docker-compose에 명시적으로 설정:

```yaml
services:
  ai-service:
    environment:
      - EC2_HOST_IP=host.docker.internal
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

이후 ai-service에서는:

```text
http://host.docker.internal:18000
```

으로 EC2 host에 안정적으로 접근 가능.

---

## 6. 핵심 이슈: **UFW**

### 처음 헷갈렸던 점

* EC2 host에서 `curl localhost:18000` → 성공
* UFW 로그에 차단 기록 없음
* 그래서 “UFW는 문제 아님”이라고 판단

👉 **이 판단은 ‘host → host’ 기준에서는 맞았다**

---

### 실제 문제의 본질

실제로 실패하던 요청은:

```
ai-service (Docker 컨테이너)
   └── 요청 →
        EC2 host :18000
```

컨테이너의 source IP는 보통:

```
172.18.0.0/16 (Docker bridge)
```

UFW 입장에서는:

* host → localhost : 내부 접근 (허용)
* **Docker bridge → host : 외부 인바운드 접근 (차단 대상)**

기본 정책:

```text
ufw default deny incoming
```

그래서 결과는:

* EC2 host에서 테스트 → 성공
* ai-service 컨테이너에서 테스트 → **Connection timeout**

---

## 7. 해결: UFW에서 18000 포트 허용

```bash
sudo ufw allow 18000/tcp
# 또는 Docker 대역만 허용
sudo ufw allow from 172.18.0.0/16 to any port 18000 proto tcp
```

### 결과

* 컨테이너 → EC2 host :18000 접근 허용
* SSH reverse tunnel 정상 동작
* ai-service → 로컬 MinerU API 요청 **즉시 성공**

👉 그래서 **“UFW 열자마자 바로 됐다”** 라는 결과가 나온 것

---

## 8. 최종 네트워크 흐름 (완성)

```
[ Local PC ]
  Docker MinerU (localhost:18000)
           ▲
           │ SSH Reverse Tunnel
           │
[ EC2 Host ]
  0.0.0.0:18000 (sshd)
      ▲
      │ UFW: 18000 허용
      │
[ EC2 Docker ]
  ai-service
  └── http://host.docker.internal:18000/file_parse
```

---

## 9. 최종 결론 정리

* ❌ ai-service 코드 문제 아님
* ❌ MinerU 문제 아님
* ❌ SSH 터널 문제 아님
* ✅ **Docker 컨테이너 → EC2 host 인바운드 트래픽이 UFW에서 차단되고 있었음**
* ✅ 18000 포트를 열어주자 전체 경로가 완성됨

---

## 10. 한 줄 최종 요약

> **SSH reverse tunnel은 이미 정상적으로 열려 있었고,
> Docker 컨테이너에서 EC2 host로 들어오는 트래픽이
> UFW 기본 정책에 의해 차단되고 있었다.
> 18000 포트를 허용하자
> `ai-service → EC2 host → 로컬 MinerU` 경로가 정상 동작했다.**

---

## 11. 시니어 관점 메모

* 핵심은 항상 **“누가 요청을 보내는가”**
* 같은 서버라도:

  * host ↔ host
  * container ↔ host
    는 **보안·네트워크 레벨에서 완전히 다르게 취급된다**
* 이 케이스를 이해하면:

  * Docker + UFW + 터널 이슈는 거의 다 설명 가능
