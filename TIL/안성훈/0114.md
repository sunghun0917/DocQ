# 📘 Nginx 공부 기록 정리

## 1️⃣ Nginx는 무엇인가

* **이벤트 기반(Event-driven) 비동기 웹 서버**
* 목적:

  * **대량 동시 접속 처리**
  * **낮은 메모리 사용량**
  * **빠른 I/O 처리**
* Apache(Tomcat) 같은 **스레드/프로세스 기반 서버의 한계를 해결**하기 위해 설계됨

---

## 2️⃣ Nginx의 기본 구조

```
Master Process
 └─ Worker Process (여러 개)
       └─ Event Loop (싱글 스레드)
```

### Master Process

* 설정 파일 로드
* 워커 프로세스 생성/관리
* 재시작, graceful reload 담당

### Worker Process

* 실제 요청 처리 주체
* **싱글 스레드 이벤트 루프**
* 수천~수만 커넥션 처리 가능

---

## 3️⃣ 핵심 개념: 이벤트 기반 + 비동기

### 이벤트란?

* 네트워크 패킷 도착
* 소켓 읽기 가능
* 소켓 쓰기 가능
* 타이머 만료

이런 것들이 **OS 커널 이벤트 큐(epoll)** 에 쌓인다.

---

## 4️⃣ 커널 큐와 워커의 관계 (중요)

### 실제 흐름

```
[OS 커널 이벤트 큐 (epoll)]
        ↓
[Nginx Worker 이벤트 루프]
        ↓
[요청 처리 로직]
```

* 커널은 **I/O 이벤트만 관리**
* 비즈니스 로직, CPU 작업은 **유저 공간(Nginx 워커)** 에서 실행

👉 **커널 큐에 “작업”이 쌓이는 게 아니다**
👉 **이벤트만 쌓인다**

---

## 5️⃣ 비동기(Asynchronous)의 정확한 의미

> **작업을 요청해두고, 완료될 때까지 기다리지 않는 방식**

* 이벤트 루프는:

  * I/O 요청 → 즉시 반환
  * 완료되면 이벤트로 통지받음
* 기다리는 동안 **다른 이벤트 처리 가능**

📌 비동기 ≠ 병렬
싱글 스레드여도 비동기 가능

---

## 6️⃣ 논블로킹(Non-blocking)과의 차이

### 논블로킹

* I/O 요청 시:

  * 못 하면 즉시 반환
* 애플리케이션이 계속 확인(polling)

### 비동기

* I/O 요청 시:

  * OS가 기다림 담당
  * 완료되면 이벤트로 알려줌

📌 **Nginx는 논블로킹 I/O + 비동기 이벤트 모델**

---

## 7️⃣ 왜 CPU 오래 쓰는 작업이 문제인가

Nginx 워커는 **싱글 스레드 이벤트 루프**다.

```text
이벤트 A 처리 중 CPU 작업 2초
→ 그 2초 동안 모든 요청 처리 중단
```

결과:

* 응답 지연 폭증
* 타임아웃
* WebSocket 끊김

👉 **CPU 작업은 치명적**

---

## 8️⃣ 스레드 풀이 등장하는 이유

> **이벤트 루프를 보호하기 위해서**

### 역할

* CPU-bound / 블로킹 작업을
* **별도의 스레드에서 실행**
* 이벤트 루프는 계속 I/O 처리

### 효과

* Head-of-Line Blocking 방지
* 서버 전체 멈춤 방지
* 응답성 유지

📌 스레드 풀은 **성능 향상이 아니라 안정성 확보 수단**

---

## 9️⃣ “스레드 풀로 던진다”의 실제 의미

1. 이벤트 루프가 이벤트 수신
2. CPU/블로킹 작업 판단 (설계 단계에서 이미 결정됨)
3. 해당 작업을 **스레드 풀 큐에 등록**
4. 이벤트 루프는 즉시 복귀
5. 풀 스레드가 작업 수행
6. 완료 후 결과를 이벤트 루프로 전달

---

## 🔟 Prefork / Worker 모델과의 차이

| 구분     | Apache Prefork/Worker | Nginx  |
| ------ | --------------------- | ------ |
| 동시성 단위 | 프로세스/스레드              | 이벤트    |
| 요청 처리  | 1 요청 = 1 스레드          | 이벤트 루프 |
| 메모리 사용 | 큼                     | 작음     |
| CPU 작업 | 비교적 안전                | 매우 위험  |
| 동접 처리  | 제한적                   | 매우 강함  |

👉 Nginx는 **“요청 수”가 아니라 “이벤트 수”를 처리**

---

## 1️⃣1️⃣ Nginx가 잘하는 것 / 못하는 것

### ✅ 잘하는 것

* 정적 파일 서빙
* 리버스 프록시
* 로드 밸런싱
* SSL 종료
* WebSocket 프록시
* 대량 동시 접속 처리

### ❌ 못하는 것

* CPU-heavy 비즈니스 로직
* 복잡한 애플리케이션 처리
* DB 연산

👉 그래서 **앞단(Nginx) + 뒤단(WAS)** 구조를 씀

---

## 1️⃣2️⃣ 한 문장 요약

> **Nginx는 OS 커널 이벤트 큐(epoll)를 기반으로 한
> 비동기 이벤트 루프 모델을 사용해
> 적은 자원으로 많은 동시 연결을 처리하는 웹 서버이며,
> CPU나 블로킹 작업은 이벤트 루프를 멈추기 때문에
> 반드시 별도의 처리 계층으로 분리해야 한다.**
