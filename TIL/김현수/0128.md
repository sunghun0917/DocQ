## 📘 TIL – 1월 27일

### Redis vs RabbitMQ vs Kafka 비교 및 설계 고민

오늘은 **Redis, RabbitMQ, Kafka의 역할과 차이점**을 정리하고,
현재 프로젝트에서 사용 중인 **Redis 기반 설계(ZSet + ACK)**가 적절한지 다시 점검해 보았다.

---

### 1️⃣ Redis, RabbitMQ, Kafka의 본질적 차이

#### 🔹 Redis

* 인메모리 기반 데이터 저장소
* 빠른 속도가 가장 큰 장점
* ZSet, List, Stream 등을 활용해 **큐·스케줄링·우선순위 처리** 가능
* 기본적으로 **경량 메시징 / 상태 관리**에 적합

#### 🔹 RabbitMQ

* 전통적인 메시지 브로커
* ACK 기반 메시지 처리 보장
* 메시지 라우팅, 재시도, DLQ 구성에 강점
* **비동기 작업 처리, 이벤트 전달**에 적합

#### 🔹 Kafka

* 대용량 이벤트 스트리밍 플랫폼
* 메시지를 “소비”하는 개념이 아닌 **로그로 저장**
* 높은 처리량과 내구성
* **이벤트 기반 아키텍처, 로그 분석, 데이터 파이프라인**에 적합

---

### 2️⃣ 현재 프로젝트의 Redis 설계

현재 구조는 다음과 같다.

* **ZSet**

  * 우선순위 또는 시간 기반으로 작업 정렬
  * 게임 진행, 이벤트 스케줄링에 활용
* **ACK 기반 처리**

  * 작업 소비 후 성공 시 제거
  * 실패 시 재시도 가능하도록 설계

이 구조를 통해:

* 빠른 처리 속도 확보
* 서버 스케줄러(JVM) 의존 최소화
* 분산 환경에서도 상태 관리 가능

---

### 3️⃣ 고민 포인트

* 현재 Redis 설계가 **메시지 큐의 역할까지 담당**하고 있음
* 규모가 커질 경우:

  * 재시도 정책
  * 장애 복구
  * 메시지 유실 방지
  * 멀티 컨슈머 처리
    를 Redis에서 직접 구현해야 함

👉 이 부분이 **RabbitMQ / Kafka 도입 필요성**을 고민하게 된 계기였다.

---

### 4️⃣ 결론 정리

* **지금 단계**

  * Redis(ZSet + ACK) 구조는 충분히 합리적
  * 구현 난이도 대비 효과가 큼
  * 게임 로직 특성상 “빠른 상태 처리”가 중요함

* **향후 고려**

  * 이벤트가 복잡해지거나
  * 로그성 데이터가 많아지거나
  * 서비스 규모가 커질 경우
    → Kafka 또는 RabbitMQ 도입 검토 필요
