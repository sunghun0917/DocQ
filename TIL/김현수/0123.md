## 📘 TIL – 1월 23일

### Redis Pub/Sub 또는 Message Broker를 고려해야 하는 이유

웹소켓 기반 게임 서비스를 배포·운영할 때, **단일 서버 구조**는 간단하지만 확장성에 한계가 있다.
동접자가 늘어나거나 서버를 수평 확장하는 순간, **서버 간 상태 동기화 문제**가 발생한다.

이때 Redis Pub/Sub 또는 Message Broker 도입을 고려하게 된다.

---

### 1️⃣ 단일 서버 구조의 한계

* 웹소켓 세션은 서버 메모리에 종속된다.
* 서버를 2대 이상으로 늘리면

  * A 서버의 유저는 B 서버의 이벤트를 받을 수 없음
* 방 단위 브로드캐스트가 서버 간에 공유되지 않는다.

👉 **수평 확장 불가**

---

### 2️⃣ Redis Pub/Sub를 사용하는 경우

**구조**

* 각 서버는 Redis 채널을 구독
* 한 서버에서 이벤트 발행(Publish)
* Redis를 통해 모든 서버에 전파
* 각 서버가 자신에게 연결된 클라이언트에게 다시 브로드캐스트

**장점**

* 구조가 단순하고 도입 비용이 낮다.
* 실시간성이 매우 뛰어나다.
* 게임 이벤트, 타이머, 상태 변경에 적합하다.

**단점**

* 메시지 영속성 없음
* 구독 중이 아닌 서버는 메시지를 받을 수 없음
* 순서 보장·재처리 불가

👉 **실시간 게임 이벤트에 최적**

---

### 3️⃣ Message Broker (Kafka, RabbitMQ 등)

**구조**

* 이벤트를 브로커에 저장
* 컨슈머가 메시지를 순차적으로 소비
* 장애 발생 시 재처리 가능

**장점**

* 메시지 영속성 보장
* 장애 복구 및 재처리 가능
* 대규모 트래픽에 안정적

**단점**

* 인프라와 운영 복잡도 증가
* 실시간성은 Redis Pub/Sub보다 다소 낮을 수 있음

👉 **로그, 이력, 점수 집계, 분석 이벤트에 적합**

---

### 4️⃣ 게임 서비스에서의 실무적 선택 기준

| 상황                  | 추천             |
| ------------------- | -------------- |
| 단일 서버               | 도입 불필요         |
| 웹소켓 서버 2대 이상        | Redis Pub/Sub  |
| 실시간 게임 이벤트          | Redis Pub/Sub  |
| 결과 저장·통계·리플레이       | Message Broker |
| 대규모 트래픽 & 이벤트 유실 방지 | Message Broker |

---

### ✅ 정리

* **Redis Pub/Sub**
  → 서버 간 실시간 이벤트 동기화용
* **Message Broker**
  → 안정성과 데이터 보존이 필요한 이벤트용
* 실무에서는
  👉 *“Redis Pub/Sub + DB”* 조합이 가장 많이 사용된다.

서버 확장을 고려하기 시작했다는 것 자체가,
이미 **운영 관점의 설계 단계**에 들어섰다는 신호라고 느낀 하루였다.
