## 📘 TIL – 1월 26일

### 게임 진행 로직은 백엔드 스케줄링이 맞을까, 프론트 레이어가 맞을까?

웹 기반 실시간 게임을 설계하면서 가장 많이 고민하게 되는 지점은
**“게임의 흐름을 어디서 제어할 것인가”**이다.

---

### 1️⃣ 프론트엔드에서 게임 레이어를 쌓는 방식

**구조**

* 프론트가 타이머·단계 전환·상태 변경을 직접 관리
* 서버는 단순 상태 저장 및 중계 역할

**장점**

* 구현 속도가 빠르다.
* 화면 전환과 애니메이션 연출이 자유롭다.
* 소규모 프로젝트나 프로토타입에 적합하다.

**단점**

* 클라이언트 조작 가능성(치팅)에 취약하다.
* 사용자별 타이밍 불일치 발생
* 새로고침·이탈 시 상태 복구가 어렵다.
* 여러 클라이언트의 “정답 타이밍”을 정확히 맞추기 힘들다.

👉 **게임 규칙을 신뢰할 수 없다**

---

### 2️⃣ 백엔드에서 게임 진행을 스케줄링하는 방식

**구조**

* 서버가 게임 상태 머신(State Machine)을 관리
* 스케줄러(또는 이벤트 기반)로 단계 전환
* 프론트는 상태를 받아 렌더링만 수행

**장점**

* 게임 규칙의 단일 진실 소스(Single Source of Truth)
* 치팅 방지 및 공정성 확보
* 사용자 재접속 시 상태 복구 용이
* 멀티플레이 환경에서 동기화가 정확하다.

**단점**

* 구현 난이도가 높다.
* 서버 부하 관리가 필요하다.
* 프론트 자유도가 상대적으로 줄어든다.

👉 **실서비스·멀티플레이 게임에 필수**

---

### 3️⃣ 실무적으로 가장 많이 사용하는 구조

👉 **권한은 백엔드, 연출은 프론트**

* 백엔드

  * 게임 단계 관리
  * 타이머 기준 시각 제공
  * 정답·판정·점수 계산
* 프론트엔드

  * 애니메이션
  * UI 전환
  * 연출 레이어 처리

예)

* 서버: “문제 시작 시각 = T, 제한 시간 = 10초”
* 프론트: `now - T` 기준으로 타이머·애니메이션 처리

---

### 4️⃣ 설계 기준 한 줄 요약

> **공정성·규칙·결과는 백엔드,
> 체감·연출·UX는 프론트**

---

### ✅ 정리

* 프론트 주도 설계 → 빠르지만 불안정
* 백엔드 스케줄링 → 안정적이고 신뢰 가능
* 실무에서는
  👉 **백엔드 중심 + 프론트 연출 분리 구조**가 정답에 가깝다.

“어디까지를 서버가 책임져야 하는가”를 고민하기 시작했다는 점에서,
게임 설계가 **단순 구현 단계를 넘어선 상태**라는 것을 느낀 하루였다.
