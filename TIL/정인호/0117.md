# 프론트/백엔드 레이어(계층) 정리

레이어를 나누는 이유는 **코드를 역할별로 분리해서**
- 찾기 쉽고
- 고치기 쉽고
- 기능 추가가 쉬운 구조를 만들기 위해서이다.

---

## Backend (Spring Boot)

### 1) Controller = "접수 창구"
- REST/WebSocket 요청을 받고 입력을 확인한 뒤 Service에 전달한다.
- 규칙 계산/DB 직접 처리 같은 무거운 일을 하면 안 된다.

### 2) Service(UseCase) = "업무 처리 담당"
- "게임 시작", "퀴즈 시작", "정답 제출", "미니게임 종료" 같은 **업무 흐름**을 실행한다.
- DB/외부 API/메시지 전송 같은 도구들을 조합해서 처리한다.

### 3) Domain(규칙) = "게임 룰(레시피)"
- 점수 계산, 이동 규칙, 버프 규칙처럼 **순수 규칙**을 담는다.
- 목표는 Spring/DB/WebSocket을 몰라도 동작하도록 만드는 것이다.

### 4) Infrastructure = "도구/외부 연결"
- Repository(DB), 외부 API Client(AI), WebSocket 전송 등 실제 연결/통신을 담당한다.

#### 의존성 방향(중요)
- Controller → Service → Domain
- Domain은 Framework/DB에 의존하지 않게 유지한다.

---

## Frontend (Vue 3 + Pinia)

### 1) Views(페이지) = "무대 감독"
- 화면 배치/라우팅/이벤트 연결을 담당한다.
- 로직이 커지면 Store/Feature로 내려보내는 것이 유지보수에 좋다.

### 2) Stores(Pinia) = "상태 관리자"
- 로비/게임 진행 상태(턴, 점수, 퀴즈, 타이머, 미니게임 상태)를 저장하고 업데이트한다.
- 서버(WebSocket/REST)에서 받은 결과를 반영하는 중심이 된다.

### 3) Services = "통신 담당(전화기)"
- REST(axios), WebSocket(STOMP) 통신만 담당한다.
- 가능한 한 "의미(비즈니스)"는 Store/Feature가 맡고, Service는 보내고/받는 역할에 집중한다.

### 4) Components = "UI 부품(레고)"
- 화면을 구성하는 재사용 부품이다.
- props/event 중심으로 만들고, store 직접 접근은 최소화하는 것이 깔끔하다.

---

## 오늘의 결론
- 역할이 섞이면(요청 처리 + 규칙 계산 + DB 처리) 나중에 리팩토링이 매우 힘들어진다.
- 그래서 **각 파일/폴더의 책임을 레이어로 나누고 의존성 방향을 지키는 것**이 중요하다.
