# TIL (2025.01.23) — 게임 흐름 제어(Flow Control) 및 큐(Queue) 시스템 구현

## 오늘의 주제
**비동기적으로 도착하는 게임 데이터와 프론트엔드 애니메이션 간의 타이밍 불일치를 해결하기 위해 `pendingQuiz` 큐 시스템을 도입하고, Git 브랜치 병합 전략을 재편**함.

---

## 진행 과정

### 1. 큐 기반의 게임 흐름 제어 (Game Flow Control)
- **`gameStore.ts`**:
  - **`pendingQuiz` 상태 추가**: 다음 퀴즈 데이터가 도착해도 즉시 렌더링하지 않고 임시 저장.
  - **조건부 퀴즈 렌더링 (`checkPendingQuiz`)**:
    - 현재 룰렛이 돌고 있거나(`rouletteTargetId` 존재),
    - 라운드 결과 연출 중(`currentRoundResult` 존재)이라면 퀴즈 표시를 보류.
    - 모든 연출이 끝나는 시점(`handleRouletteComplete` 등)에 대기 중인 퀴즈를 적용.
  - 이를 통해 "룰렛이 도는 중에 다음 문제가 튀어나오는" 치명적인 UX 결함 해결.

### 2. 스토어 구조 리팩토링
- **`gameStore.ts`**:
  - 외부 컴포넌트에서 필요한 상태(`gameStatus`, `timeRemaining`)가 제대로 export 되지 않던 문제 수정.
  - 중복 선언된 액션과 상태들을 정리하여 코드 클린업.

### 3. Git 병합 전략 수립
- **`develop` 브랜치와의 충돌 해결**:
  - 로컬 `merge` 시도 시 `WaitingView`와 `gameStore`에서 대규모 충돌 발생.
  - 무리한 로컬 병합 대신, 현재 작업본을 `fix/restore-game-logic` 피처 브랜치로 푸시하고 **GitLab MR(Merge Request)**을 통해 코드 리뷰 후 병합하는 안전한 방식을 택함.

---

## 문제 상황 및 해결

### 1. 비동기 이벤트 레이스 컨디션 (Race Condition)
- **문제**: 백엔드 메시지(`/quiz`)가 프론트엔드 애니메이션보다 빨리 도착하여 UI가 꼬임.
- **해결**:
  ```typescript
  // 퀴즈 수신 시 바로 적용하지 않고 조건 검사
  if (movementInProgress.value || currentRoundResult.value || rouletteTargetId.value) {
      pendingQuiz.value = quizData; // 큐에 저장
      return;
  }
  ```
  - 위와 같은 **지연 처리 로직**을 도입하여 프론트엔드가 주도권을 갖고 화면 전환을 제어하도록 개선.

### 2. 머지 충돌 (Merge Conflict)
- **문제**: `develop` 브랜치에 우리보다 앞선 기능(미니게임 등)이 추가되어 있어, 단순 병합 시 코드가 꼬일 위험 큼.
- **해결**: 로컬 병합을 중단(`merge --abort`)하고, 우리 브랜치의 변경 사항을 명확히 격리하여 MR을 올림으로써, 충돌 해결 책임을 분산하고 코드 안정성을 확보.

## 배운 점
- **프론트엔드 주도적 UX 제어**: 서버가 데이터를 보냈다고 해서 무조건 바로 보여주는 것이 정답은 아니다. **사용자가 인지할 시간을 벌어주는 완충 장치(Queue)**가 필요하다.
- **Git 전략의 유연성**: 충돌이 너무 심할 때는 억지로 고치려 하기보다, 작업을 독립된 브랜치로 보존하고 전략적인 병합 시점을 잡는 것이 낫다.

---

## 오늘의 회고
- 어제 분석했던 타이밍 이슈를 오늘 `pendingQuiz`라는 깔끔한 로직으로 해결해서 매우 만족스럽다.
- 게임이 끊김 없이 매끄럽게(물 흐르듯이) 진행되는 것을 보니, 코드가 사용자 경험에 미치는 영향을 다시 한번 실감했다.
- `develop` 브랜치와의 병합은 여전히 과제로 남아있지만, 기능 단위로 확실하게 복구해두었기에, 이후 작업도 차분히 진행할 수 있을 것 같다.
